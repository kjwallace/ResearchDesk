## Summary of `scripts/generate_emails_llm.py`

The model only writes the text of each email (sender, sender email address, subject, body, and the reason for its label). The labels themselves come from the plan file made by `generate_email_plan.py` and are attached in code after each response comes back. That makes the labels in the output exactly the ones each email was written for.

**Inputs for each day**
- `data/corpus/day N/email_plan.jsonl` has one slot per email: `email_id`, `triage`, `email_type`, `affected_tickers`, `additional_labels`, `human_attention`, `systemic`, `angle`, and `day`.
- Any drafts already in `scripts/drafts/day_N/` are skipped, so a rerun only fills in the missing slots.

**How each request is built**
- The **system prompt** has three parts:
  - Your `synthetic_data_prompt.md`, word for word.
  - A context block. It sets the scene: the fictional fund Larchmont Ridge Capital, its desk members, the inbox date, and the late-October earnings dates. It also defines the exact label names, since the prompt file says `relevent` in one place and `thesis_relevant` in another.
  - Five of my hand-written emails from `scripts/style_examples.json` as style examples. They cover `thesis_relevant`, `redundant`, `low_value`, and `irrelevant` labels, and the model is told not to reuse their scenarios.
- The **user message** has three parts:
  - The subjects already in that day's inbox, so the model doesn't repeat scenarios. For day 2 this also includes day 1's subjects, marked as yesterday's, so day 2's redundant emails can rehash them.
  - The slot specs for the batch.
  - Strict output rules: return only a JSON array with the six text fields.

**API call**
- It posts to the Anthropic Messages API using only Python's standard library, with the key loaded from `.env`.
- The default model is Claude Sonnet 5.5, with temperature 1.0 for variety and 16,000 max tokens. A response cut off at the token limit is rejected.

**Checks on every response before it's saved**
- The email IDs come back in the same order as the slots, and every text field is non-empty.
- Every ticker in `affected_tickers` is actually named in the email.
- If an email names a target company three or more times without that ticker being in its `affected_tickers`, it's rejected. This keeps noise emails from quietly being about a target company.
- A failed check or a temporary API error (rate limit or overload) triggers a retry with increasing waits, up to five attempts. A batch that still fails is reported and filled in on the next run.

**Output**

Each email is merged with its slot into one record. The first ten fields are the prompt's schema; the last four are the generation labels:

```python
{"email_id", "sender", "sender_email", "subject", "body",
 "triage", "additional_labels", "affected_tickers", "human_attention", "reason",
 "email_type", "systemic", "angle", "day"}
```

A final check confirms every label field matches the plan. Each batch is saved to `scripts/drafts/day_N/llm_<first email_id>.json`. `build_email_jsonl.py` then combines all the batches into `data/corpus/day N/emails.jsonl`, checks that all 300 slots are present, and prints the label distribution so it can be compared against the plan.

**Batching**
- Batches hold 6 emails, and 6 batches run in parallel as a "wave".
- Each wave's subjects are added to the inbox list before the next wave starts, so later batches can see what's already been written.

**Command-line options:** `--day`, `--model`, `--batch-size`, `--workers`, `--max-tokens`, `--limit` (draft only a few slots), and `--dry-run` (print the full request without calling the API).
