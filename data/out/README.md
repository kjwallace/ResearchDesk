# Pipeline outputs

`uv run python -m triage_app.pipeline.run --set <set>` writes one folder per corpus set: `day_1/`, `day_2/` (the test days) and `tuning/`. Each file below is a JSON list of one contract from `src/triage_app/schema.py`, unless it says otherwise. The files are the only interfaces between stages; any stage reruns alone (`--stage <name>`, or `--from <name>` onward).

All data is synthetic.

## Inputs that are not output files

- **The emails** are not written here. Every stage, the evals and the web app read them from `data/corpus/<set>/emails.jsonl` through the corpus loader (`triage_app.corpus.load`), which drops every label. They are `Email` objects with bodies exactly as in the corpus, in arrival order. Every quote is checked against that body after whitespace collapse.
- **Thresholds**: `tuned/thresholds.json` (see below) or the starting values in `src/triage_app/thresholds.py`.

## Files in `data/out/<set>/`, in pipeline order

| Stage | File | Contract | Read by |
| --- | --- | --- | --- |
| 2 Check for repeats (`redundancy`) | `redundancy.json` | `RedundancyRecord`, **flagged emails only**: each potential repeat, the earlier email it repeats (`nearest`) and both similarity scores. An email absent from the file was not flagged. No vectors are saved. | Stage 4, stage 5, the evals (`repeat_flagged`, `repeat_precision`), the app's audit and email pages, the live route |
| 3 Classify (`classify`) | `triage.json` | `TriageRecord`: Jev's answers, unmodified, one per email, with the criteria version in force. Includes `human_attention` and the display-only `email_type` / `email_type_probs`. | Stage 4, stage 9 (attention order and alerts), the evals, tuning, the app |
| 4 Label and gate (`gate`) | `results.json` | `EmailResult`: one label of record (or quarantine), the gate decision and a one-line reason written by code, one per email | Stages A and 5 to 9, the evals, the app |
| A Attention notes (`human_attention`) | `notes.json` | `AttentionNote`: summary, why it needs a person, the action and any deadline, with verified quotes, one per email flagged for human attention | Stage 9, the evals, the app |
| 5 Extract (`extract`) | `claims.json` | `Claim`, IDs `<email_id>.c<n>`, from emails that passed the gate | Stages 6 and 7, the app |
| 6 Analyze (`analyze`) | `analysis.json` | `AnalysisRecord`: skills called and suggestions made, or a no-change reason, one per passed email | Stage 9, the app |
| 6 Analyze | `suggestions_raw.json` | `Suggestion`, IDs `<email_id>.s<n>`, all open | Stage 7 |
| 7 Validate (`validate`) | `suggestions_checked.json` | `Suggestion`, open (possibly adjusted) or rejected with a reason | Stage 8, the evals, the app's audit view |
| 8 Merge and rank (`merge`) | `suggestions.json` | `Suggestion`, merged per pillar and stance (`<pillar_id>.<stance>`, `<ticker>.new<n>`) | Stage 9, the evals, the app |
| 9 Deliver (`deliver`) | `brief.json` | `Brief` (one object): counts, the suggestion lists, needs attention, relevant with no link, alerts, audit and quarantine lists | The app, `SUMMARY.md` |
| End of `run.py` | `metrics.json` | `UsageReport` (one object): run-level token use and latency per stage and per model, cache hits, spent vs uncached tokens, latency percentiles, tokens per email, total time. Per-call records are kept in memory only. | The app's Monitor page, `SUMMARY.md` |
| End of `run.py` | `SUMMARY.md` | Markdown, generated by `pipeline/summary.py`: set and date, criteria version, tuned or starting thresholds, emails by label and gate, flagged repeats, attention notes, suggestions by brief list with ID and rationale, alerts, and the monitoring headline. It never holds an email body or a corpus label. | People |
| Eval script (`evals.score`) | `eval.json` | `EvalReport` (one object): every measure against the corpus labels (including `email_type_accuracy`), the confusion matrix and every miss | The app's Eval page |
| Eval script | `review_notes.csv`, `review_suggestions.csv` | Hand-review sheets; rewritten until a person fills a check | The eval script |
| Criteria check (tuning only) | `criteria_check/<version>.json` | `EmailResult` per tuning email under one criteria version, to list label changes | The criteria check |

## Files outside the set folders

| File | Contract | Written by | Read by |
| --- | --- | --- | --- |
| `data/out/criteria_history.json` | `CriteriaHistoryEntry`, one per criteria version: the criteria files' text, label measures on the fit and validation splits, and the tuning emails relabeled since the previous version | `evals.criteria_check` | The app's Criteria page |
| `tuned/thresholds.json` | `Thresholds` (one object): the swept gate thresholds (`pass_signal`, `human_attention`, per-ticker and per-topic). The redundancy thresholds in it are ignored; they stay fixed in `thresholds.py`. | `evals.tune` (tuning set, fit split) | Stage 4 and every reader of `RunContext.thresholds` |

## Renamed keys

Older files may still use earlier names: `kind` / `kind_probs` / `attention` in `triage.json`, `attention` in `tuned/thresholds.json`, `attention_precision` / `attention_recall` in `eval.json` and `criteria_history.json`, and the `attention` stage in `metrics.json`. `uv run python scripts/rename_output_keys.py` rewrites them in place to `email_type` / `email_type_probs` / `human_attention` (idempotent). Old six-option `email_type` values stay until the next classify run.

Files earlier runs wrote that the pipeline no longer writes, and that can be deleted: `raw.json`, `parsed.json`, `vectors.npy`, `usage.json`.
