# Work package 6a: Extraction, analysis agent, skills, verify agent

**You own:** `src/triage_app/modules/extract.py`, `modules/analysis_agent.py`, `modules/skills.py` (one DSPy module per skill, registered by name — or one file per skill under `modules/skills/` if you prefer), `modules/verify_agent.py` (all new), `src/triage_app/pipeline/extract.py`, `src/triage_app/pipeline/analyze.py`, and tests `tests/test_extract.py`, `tests/test_analyze.py`, `tests/test_verify.py`. (Package 6b owns validate.py and merge.py — do not touch them.)

**SPEC sections:** "Analysis agent" (all rules and mechanics), "Read-through links", "How an email meets the book", "Kinds of suggestion", "Data contracts", "Stage files", "Data flow" (stage 5 and the verify agent paragraph), design rules.

**Build:**
1. Extraction (stage 5): DSPy module, instructions from `instructions/extract_claims.md`, output `list[ClaimDraft]`, model `config.ANALYSIS_MODEL` via `RouterLM` + JSONAdapter. `pipeline/extract.py` `run` reads `parsed.json`, `results.json`, `redundancy.json`; runs only for `gate == "pass"` emails; when the email's redundancy record is flagged, pass the nearest earlier email's parsed body as context and keep only claims it did not make (skip it if that earlier email was quarantined). Each claim's quote checked with `quote_in`; failures dropped and counted. Code assigns IDs `<email_id>.c<n>`. Writes `claims.json`.
2. Skills: `alter_existing_thesis` and `spawn_new_thesis`, each its own prompt file (`skills/*.md`, generated by package 1) and its own DSPy module returning `SkillResult`. The existing-thesis skill sees the claims and candidate pillars with stance and linked drivers (label, unit, desk value, consensus) — never size or conviction. The new-thesis skill sees one ticker, that company's pillar statements and its drivers' IDs, labels and units. Both see Jev's label (from results.json, never the corpus label).
3. Analysis agent (stage 6): a tool loop (e.g. `dspy.ReAct` or a small explicit loop) whose tools are built from `tools/analysis_agent.json` (name, description + `returns` appended, input schema); each tool runs one skill module; at most `config.SKILL_CALLS_PER_EMAIL` calls; the agent is given the claims and the statements of the candidate pillars and passes claim IDs only. **Code picks candidate pillars**: every pillar of each company in the claims' tickers plus the pillars `data/seed/links.json` ties to those companies (load the book with `state.fold.load_seed()` / `fold(seed, [])`). **Code collects output**: suggestions come from the skills' parsed results, never from the agent's final text; `no_change_reason` is the last skill's reason, or the agent's final text only when no skill was called; code writes "no claims extracted" when there are no claims. Raw suggestions get IDs `<email_id>.s<n>`, status open, and code fills `LinkedAssumption.book_value`/`consensus_value` from the book. `pipeline/analyze.py` writes `analysis.json` and `suggestions_raw.json`.
4. Verify agent: module checking one suggestion against `data/filings/<TICKER>_10-K.txt` (paragraph search by embedding similarity with `ctx.embedder`, returns nothing when no filing) and the session change log (word match), tools from `tools/verify_agent.json`, at most `config.VERIFY_TOOL_CALLS` calls, returns `VerifyResult`. No tool writes, sends or browses. Expose `verify(suggestion, log, ctx) -> VerifyResult` for the web app.

**Tests (fakes only):** extraction drops a non-matching quote and counts it; repeat-context path; candidate-pillar selection including links; the agent never exceeds three skill calls; suggestions come from skill results not final text; no-change reasons; code-filled book values; IDs; every output validates; prompts never contain size/conviction or label fields. Use the fixture stage files as inputs.

**Done when** the above passes on the fixtures. You may run extract + analyze live once on the fixture emails (through the cache) and report tokens/latency. Do not run a full corpus set.
